## Exact-head review corrections (P1/P2)

This section is binding for the later implementation and records the two defects found by the exact-head review before any implementation work. It does not authorize a runtime action in this documentation turn.

### P1 — post-create marker crash gap

The previous contract had a narrow ordering gap: `candidate` was written with a target network ID still `absent`, `docker network create` could then succeed, and a process/SSH/host interruption could occur before the required candidate rewrite. Recovery compared the marker's `absent` value with the live network ID and rejected the mismatch, so the helper could neither prove ownership nor safely roll back. The impact is limited to a run-created target network and its marker-bound recovery; it must never widen into adoption of an existing or foreign network.

The only admissible recovery exception is the **post-create marker adoption** rule below. It is evaluated independently for each expected target network while both host locks are held:

1. The marker is `candidate` (or is being atomically moved to `rolling_back`), its `transaction_manifest_sha256` is a full hash, and the canonical manifest is read back byte-for-byte with the same hash. The manifest's `transaction_id`, owner, target name, and `created_by_run_authorized=true` all match the transaction being recovered; the manifest's baseline presence for that target is exactly `absent`.
2. The live engine inventory contains **exactly one** network with that expected name. Its full ID, `driver`, `scope`, `internal`, default IPAM/options, `com.catering.owner`, `com.catering.phase`, `com.catering.kind`, and `com.catering.transaction=<manifest.transaction_id>` match the manifest and the target contract exactly. A network that is merely owner/phase/kind-labelled, has another transaction label, or is discovered through a different name is not adoptable.
3. The post-create window has no subsequent membership mutation: the target network has the exact stage-allowed member/alias set for the marker's last confirmed step (normally empty immediately after `create`), no unexpected member, alias, network option, attached-container host-port binding, or other resource, and no duplicate/unknown target network exists. A non-empty set is admissible only when it is exactly the already-confirmed stage set; any member that could only have been added after the missing marker rewrite makes the case `NO-GO`.
4. The helper atomically writes the full network ID into the state-bound progress/marker record, preserving the same owner, state, transaction ID and manifest hash, then reads the record back and revalidates the live ID/labels. Evidence-only adoption, an in-memory variable, or a changed baseline manifest is insufficient. Only after this readback may the helper continue at the next deterministic stage or atomically enter `rolling_back` and perform the owner-scoped rollback sequence.

Every ambiguity remains fail-closed: zero matches, two matches for one expected name, an unexpected member/alias/port, a foreign container, a wrong label/parameter/transaction, an unbound or mismatched manifest, a marker ID that is already non-absent but differs from live state, or a failed atomic readback is `NO-GO` with no adoption and no deletion. No generic "same name" or "same owner" adoption is permitted.

The two-network cases are deterministic. Network creation order is `catering_ingress` first and `catering_private` second. If the process stops after the first create and before its marker rewrite, an exact empty transaction-labelled `catering_ingress` plus absent `catering_private` is the only valid between-creates state: adopt only ingress, atomically bind its ID, then create/verify private. If ingress already has a bound ID and the process stops before private's rewrite, validate that ID and apply the same rule to exactly one empty private network. If both creates completed before progress was persisted, both expected names may be adopted together only when each target independently satisfies the rule, there is exactly one match per name, and the pair is atomically written in canonical ingress-then-private order. A private-only resource while ingress is absent, two resources for one target, or any extra/foreign resource is an out-of-order or ambiguous state and remains `NO-GO`; it is never bulk-adopted. A matching run-created resource may be owner-scoped rolled back only after this proof, the exact full ID, emptiness/no-foreign-consumer check, and transaction label are revalidated.

### P2 — stage-aware compatibility invariants

The previous wording treated the complete member set of `platform-infra_default` and `zeiterfassung_default` as an immutable baseline after every mutation, while §2.2 explicitly detaches Catering members from those networks. That is contradictory. The corrected invariant partitions each compatibility network into an immutable foreign-app portion and a stage-controlled Catering portion:

- Zeiterfassung, EventOS, Iranmonitor and Shared Edge retain their exact baseline container IDs, `RestartCount`, status/`StartedAt`, images, Compose identities, network IDs, aliases and host-port bindings at every stage. Their member/alias entries on compatibility networks are unchanged; no foreign-app detach, connect, recreate, restart or additional member is allowed.
- Catering members may change only by the ordered owner-scoped transitions in the matrix below. No extra Catering member, alias, port binding or network attachment is allowed, and no transition may skip a row or detach more than the named member.
- The last remaining **Catering** consumer (the last occupied Catering compatibility consumer) on a compatibility network is detached only after its replacement route, DNS/port identity and all-host smokes are green. The compatibility network itself is retained because foreign consumers remain; a green replacement proof never authorizes deleting the network or touching a foreign member.
- Rollback must restore the exact baseline Catering and foreign member sets and every baseline alias, then re-run the foreign invariants. A partial re-add or a name-only alias is not an exact rollback.

### P1-A — candidate before protected-source installation

The exact-head review found a second ordering gap: the previous sequence installed the protected Platform/Edge source copies while the marker was still `absent`/`inactive`. A crash could therefore leave changed sources plus an unbound baseline manifest and no marker-authorized recovery transaction. The source copies must never be adopted from that stable-looking state.

The corrected source transaction is strict and state-bound:

1. Under both locks, capture the complete baseline and atomically install/read back/hash the immutable canonical manifest. The manifest records the prior marker state, prior source presence/hashes, exact rollback artifacts, both baseline network statuses/IDs, and the expected Platform/Edge source hashes.
2. Before **any** source write/rename or network mutation, atomically write/read/validate `candidate`. Its canonical fields include `transaction_id`, `transaction_manifest_path=/opt/catering-phase3/phase3.transaction-baseline.manifest`, the exact `transaction_manifest_sha256`, the two expected source hashes, a deterministic `baseline_network_status` projection (`catering_ingress=<absent|pre-existing-exact>;catering_private=<absent|pre-existing-exact>`), and the confirmed network IDs (initially `absent` where the baseline proved absence). The marker-to-manifest transaction/owner/path/hash binding is checked byte-for-byte before proceeding.
3. Install the protected Platform source copy atomically, read it back and hash/cmp-verify it against the candidate's expected hash; then install/read back/hash the protected Edge source copy under the same contract. A source progress field is advanced only after its copy readback succeeds. If a crash occurs after a source rename but before its progress rewrite, the candidate remains authoritative: exact expected hash means idempotent `verified` progress may be written; any mismatch is `NO-GO`/owner-scoped rollback. A source hash is never adopted merely because the stable marker is absent/inactive.
4. Only after both protected copies are verified against the candidate and manifest may the helper create/verify networks, perform the existing P1 exact-one post-create adoption rule, connect members, detach compatibility memberships, and eventually write `active`. `candidate` remains present across every source/network interruption; normal callers remain blocked.

`absent`/`inactive` plus a canonical manifest or any changed protected source without a valid marker-bound finalization proof is `NO-GO`. The only safe handling of a manifest staged before the candidate write is to verify that no source/network state changed, remove that unbound staged manifest atomically under both locks, restore the exact prior stable state, and stop with `NO-GO`; it is not a continuation path. If any source or network did change while the marker was absent/inactive, no stable-state special case may adopt it.

### P1-B — receipt-bound, idempotent rollback finalization

The previous rollback sequence could remove the canonical manifest before the prior marker was durably restored, leaving `rolling_back` without its recovery authority. The fixed fifth protected path is `/opt/catering-phase3/phase3.rollback-completion.receipt`. It is non-secret, atomically written/read back under both locks, outside all general sync/delete/snapshot/restore trees, and never replaces runtime rollback or the immutable baseline manifest.

The receipt is valid only when its canonical record contains exactly `schema=phase3.1.rollback-completion`, `transaction_id`, `transaction_manifest_path`, the exact `transaction_manifest_sha256`, `prior_marker_state=absent|inactive`, the exact prior marker hash or `absent`, and a `restore_evidence_sha256` bound to the complete source/network/member/foreign-invariant/smoke restore proof. It is written only after that proof is complete. A receipt with a mismatched transaction, manifest hash/path, prior state, or restore-evidence hash is `NO-GO` and cannot authorize cleanup.

Rollback finalization is a two-phase, idempotent sequence:

1. Keep `rolling_back` plus the marker-bound canonical manifest while restoring sources/memberships and running all invariants/smokes. Atomically write/read/validate the completion receipt only after the restore proof is complete.
2. With the valid receipt and manifest still present, atomically restore the exact prior marker: write/read `inactive` with its exact prior fields, or atomically remove the marker when the prior state was `absent`. The receipt and manifest remain present until the stable readback succeeds.
3. After stable prior marker/absence plus receipt has been read back and authenticated against the manifest, archive the immutable manifest proof in separate Evidence and atomically remove the canonical manifest. Read back the stable prior marker/absence plus receipt with `manifest=absent`.
4. Only after that readback atomically remove the completion receipt and read back the clean prior stable state. Terminal `PILOT: ROLLED BACK` is allowed only then.

The only resumable finalization windows are therefore exactly:

| Authenticated state | Recovery action; no new runtime rollback is inferred |
| --- | --- |
| `rolling_back` + manifest + receipt | Validate receipt ↔ manifest ↔ prior-state/evidence binding; repeat only the prior-marker restore step. |
| Stable prior marker/absent + manifest + receipt | Validate the receipt and stable marker/absence; repeat only manifest archive/removal. |
| Stable prior marker/absent + no manifest + receipt | Validate the receipt against the archived restore proof and stable prior state; remove only the receipt. |

`rolling_back` without the canonical manifest is `NO-GO`; stable prior marker/absence with a manifest but no valid receipt is `NO-GO`; a receipt alone never authorizes runtime restore. A receipt is not written early to make a rollback look complete. Any interruption before receipt creation leaves `rolling_back` plus manifest for normal rollback recovery; any interruption after each listed atomic write/rename/remove is handled by exactly one of the three authenticated states above. The receipt path is included in every protected-path exclusion, mutator/allowlist validation, and RED/static contract.

#### Marker/manifest/receipt crash-point table

Every atomic write, rename, or remove has one authenticated state before and after it. The helper must make the operation idempotent by re-reading the post-state before retrying; it may not infer progress from an in-memory flag or from a stable marker alone.

| Atomic operation | Authenticated pre-state | Authenticated post-state / idempotent recovery |
| --- | --- | --- |
| Install baseline manifest | Stable prior marker/absence + no manifest + no receipt; protected sources/networks equal baseline | `pre_candidate_manifest(staged, self-hash)` + stable prior marker/absence + no receipt, with no source/network mutation; this is lock-held and not a stable state. If interrupted, verify baseline and remove only this unbound staged manifest, then stop `NO-GO`. |
| Remove interrupted pre-candidate manifest | `pre_candidate_manifest` + stable prior marker/absence + no source/network mutation | Stable prior marker/absence + no manifest + no receipt; the transaction stops `NO-GO` and cannot continue from an unbound source/manifest. |
| Install candidate marker | `pre_candidate_manifest` + prior marker/absence + no source/network mutation | `candidate` + exact manifest path/hash, transaction ID, expected source hashes, baseline network status and source progress `pending`; normal callers block. |
| Install/read back Platform source copy (atomic temp→rename) | `candidate` + manifest + Platform progress `pending` | Same `candidate`/manifest + exact expected Platform hash, with Platform progress still `pending`; an interrupted rename is resolved only by exact hash inspection. |
| Commit Platform source progress | `candidate` + manifest + exact expected Platform hash + Platform progress `pending` | Same `candidate`/manifest + Platform progress `verified`; a mismatch is rollback/`NO-GO`, never adoption. |
| Install/read back Edge source copy (atomic temp→rename) | `candidate` + manifest + Platform `verified` + Edge `pending` | Same `candidate`/manifest + exact expected Platform/Edge hashes, with Edge progress still `pending`; an interrupted rename is resolved only by exact hash inspection. |
| Commit Edge source progress | `candidate` + manifest + exact expected Platform/Edge hashes + Edge progress `pending` | Same `candidate`/manifest with both source-progress fields `verified`; a mismatch is rollback/`NO-GO`, never adoption. |
| Create/bind each new network | `candidate` + both sources verified + target ID `absent` or confirmed | `candidate` with the full confirmed ID; a missed bind is recovered only by the existing P1 exact-one adoption proof. |
| Write active marker | `candidate` + manifest + both sources verified + complete network/membership/smoke evidence | `active` + same transaction/path/hash, exact installed source hashes, verified progress, and full network IDs; if interrupted, read back and distinguish the authenticated candidate pre-state from the authenticated active post-state before retrying. |
| Enter `rolling_back` | `candidate`/`active` + manifest, or an already valid `rolling_back` + manifest | `rolling_back` + same manifest hash and all confirmed/adopted provenance; no receipt yet until restore proof. |
| Restore each protected source artifact (atomic rename/remove) | `rolling_back` + manifest + no receipt | Same `rolling_back` + manifest with exact prior source presence/hash evidence accumulating; no stable marker or manifest removal is allowed. |
| Restore membership/alias state | `rolling_back` + manifest + no receipt + source restore evidence | Same `rolling_back` + manifest with exact P2 `S0` membership/alias and foreign-invariant evidence accumulating; no stable marker or manifest removal is allowed. |
| Write completion receipt | `rolling_back` + manifest + complete restore/invariant/smoke proof | `rolling_back` + manifest + authenticated receipt; receipt fields bind transaction, exact manifest hash/path, prior state and restore proof. |
| Restore prior marker or atomically remove prior-absent marker | `rolling_back` + manifest + valid receipt | Stable prior marker/absence + manifest + same receipt; interruption is resumed from this state, never by deleting the manifest first. |
| Archive receipt-bound proof | Stable prior marker/absence + manifest + valid receipt | Same stable prior marker/absence + manifest + valid receipt plus read-back archived proof; interruption retries proof validation, never removes the canonical manifest early. |
| Remove canonical manifest | Stable prior marker/absence + manifest + valid receipt + archived proof | Stable prior marker/absence + no manifest + valid receipt; interruption is resumed by receipt validation and receipt-only cleanup. |
| Remove completion receipt | Stable prior marker/absence + no manifest + valid receipt | Stable prior marker/absence + no manifest + no receipt; only now terminal `PILOT: ROLLED BACK`. |

The atomic sequence is fixed: (a) acquire both locks; (b) capture the complete baseline; (c) atomically install the immutable canonical baseline manifest, fully read it back, and hash it; (d) before any source write/rename or network mutation, atomically write/read/validate `candidate` with the exact transaction ID, manifest path/hash, expected source hashes, baseline network status, and pending source progress; (e) atomically install/read back/hash the Platform source and then the Edge source, advancing each progress field only after its own readback; (f) only then create `catering_ingress`, bind its full ID before any next mutation, create `catering_private`, and bind its full ID before any next mutation; (g) if an interruption occurs before either bind, invoke only the P1 exact-one adoption rule under both locks and atomically bind the recovered ID(s), otherwise stop; (h) complete the runtime migration and all separate Evidence-/Laufmanifest records as a non-terminal `PILOT: GO CANDIDATE`; (i) atomically write `active` with the same manifest hash, full source hashes, verified source progress, and network IDs and fully read it back; (j) run final invariants and smokes; (k) only then emit terminal `PILOT: GO`. The crash-point table is normative for every write, rename, and remove, and no retry may proceed without authenticating its post-state. No text or helper branch may emit terminal GO before successful active readback.

Rollback uses exactly the marker-hash-bound canonical baseline manifest. Its fixed sequence is: (a) under both locks, atomically write/read `rolling_back` while preserving the same `transaction_manifest_sha256`; (b) if a post-create marker gap is present, apply the P1 exact-one proof and atomically bind the recovered ID before any removal; (c) validate the canonical manifest and restore the exact prior protected source presence/hashes and owner-scoped rollback artifacts; (d) additively restore every exact old Catering/Edge compatibility membership and alias according to the reverse P2 matrix; (e) run all foreign invariants and smokes; (f) remove new pilot memberships one at a time and only networks whose `created-by-run` authorization is proven by the immutable baseline plus exact owner/transaction labels; (g) rerun invariants, smokes, source checks, and manifest/provenance checks without requiring removed resources to remain live; (h) only after complete restore/invariants/smokes atomically write/read the fixed completion receipt bound to the transaction ID, exact manifest path/hash, prior marker state/hash, and restore-evidence hash; (i) with valid receipt and manifest still present, atomically restore/read the exact prior `inactive` marker or atomically remove/read the marker when prior state was `absent`; (j) archive/read back the receipt-bound manifest proof and only then atomically remove/read the canonical baseline manifest, leaving the receipt; (k) only after stable prior + no manifest + valid receipt is read back atomically remove/read the receipt; (l) only then emit terminal `PILOT: ROLLED BACK`. There is no transition directly from `active` to `inactive` at rollback start. Any process/SSH/workflow/host interruption or other failure leaves one of the three authenticated finalization states (or `rolling_back` + manifest before receipt), normal callers blocked, and terminal outcome `PILOT: NO-GO`.

General Platform/Web/Edge rsync, snapshot, and restore paths must exclude `/opt/catering-phase3` mechanically and must not copy, delete, or overwrite any protected path. Every normal mutating caller validates the marker, canonical manifest, exact manifest hash/transaction context, lock order, mode-specific file chain, source hashes/progress, baseline network status, network IDs, rendered-config evidence, and the completion-receipt rules before mutation: active plus missing/hash-false sources or manifest is `NO-GO`; inactive/absent plus templates and no baseline manifest is Phase-2-safe; a pre-candidate staged manifest is cleanup-only and never a stable shortcut; candidate/rolling_back is always blocked. `stable prior + manifest` without a valid receipt and `rolling_back` without a manifest are forbidden. The pilot helper's `rolling_back` path instead validates the same immutable manifest proof while resources are restored or removed and handles only the three receipt-bound finalization states.

The separate non-secret Evidence-/Laufmanifest records marker state/path, prior and new marker hashes, the immutable baseline manifest hash/path, the fixed completion-receipt path/hash and prior-state binding, both protected source hashes/paths, network IDs/members, provenance, rendered Compose/config hashes, mode, lock order, smokes, restore evidence, and rollback artifacts without secrets, environment values, credentials, or protected file/mount contents. It is append-only run evidence and never replaces the canonical baseline or receipt.
